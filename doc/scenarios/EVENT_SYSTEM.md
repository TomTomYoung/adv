# フィールド・戦闘イベント仕様

更新日: 2026-09-23。作品版1.17.0。配置・条件・命令はJSONで宣言し、Coreが発火と進行を管理する。Viewは本文・選択肢・戦闘を表示する。[登録一覧](EVENT_CATALOG.md)、[クエスト配置](QUEST_EVENTS.md)、[命令仕様](SCRIPT_REFERENCE.md)も参照する。

## フィールドイベント

強制イベントは、発火条件が成立した時点でCoreが自動的に開始する。開始ボタンは不要。開始後の台詞送りや物語上の選択肢はプレイヤーが操作する。

1. `enter`：指定セルへの進入で発火。歩行・梯子などのセル移動と、階段・ワープ・迷宮入場による到着が対象。map/x/y/zが一致する足元セルで判定し、正面のセルや向き変更だけでは新たな進入にならない。`condition`・`visibleWhen`・`once`も検査する。
2. `auto`：条件成立で自動発火。受注中クエストの `events` に定義する。`condition` と `once: true` が必要。`points: []` はセル指定なし、座標を並べればそのセルだけが対象。`dungeon` があれば対象迷宮を限定する。会話・戦闘・命令処理が終わった時点でも再判定する。
3. `interact`：プレイヤーが「足元・正面を調べる」を選ぶと、足元または通行可能な正面の配置物を調べる。壁灯や宝箱などの任意調査に使う。
4. `action`：「調べる」で開いたメッセージ内の選択肢から明示実行する。常設の操作パネルは設けない。使用条件・所在・高さ・実行済み記録はCoreが再検査する。

`enter` と `interact` はマップオブジェクトへ投影し、`auto` と `action` はクエスト定義から直接判定する。クエスト専用イベントの正本は `authoring/quests/qXXX.events.json`、配布先は `data/quests/qXXX.json`。共通マップの配置物にも `enter` を指定できる。

## 発火順と保存

`src/core/field-events.js` が共通処理を担当する。会話、選択、戦闘、未完了の命令列がある間は別のフィールドイベントを開始しない。セルに到着すると、配置物の進入イベント、物語の到着処理、セルレイヤーの進入イベント、クエストの条件自動イベント、通知された迷宮の条件付きイベントの順に判定する。同じ種類の複数イベントはデータの定義順で実行する。

移動時の地形・水没・ダンジョン固有処理の後、通常の危険判定とランダム遭遇の前にイベントを判定する。先にダンジョン固有処理で会話・戦闘が始まった場合は、その終了までセルの進入記録を保留する。

`state.fieldEntry` は現在の進入セルと、この進入で開始した配置IDを保持する。実行前にIDと `state.events` の開始回数を記録する。同じセルで会話を中断・保存・再読込しても、同じ進入イベントを最初から繰り返さない。セルから離れて再進入すると再判定する。`once: true` の配置はセーブを通じて一度限り。

条件自動イベントは `state.events[quest/クエストID/イベントID]` に一度限りの記録を保存する。条件が真のままでも再実行しない。再訪で繰り返す内容には `enter` を使う。複数段階の自動条件は別のIDと条件で定義する。

進入イベントが会話・戦闘を始めると、後続イベントは待機する。終了後に現在の条件を再評価する。処理途中で移動した場合は移動先のセルで判定する。命令位置は既存のVMに保存する。連鎖処理には実行上限がある。

## 環境変化を購読する条件付きイベント

迷宮の正本 `authoring/dungeons/*.json` に `fieldEvents` を定義する。`data/dungeons.json` へ生成する。現在は篝火の迷宮に通常襲撃を1件登録し、既存の `fire_network.danger` は廃止した。

```json
{
  "id": "unprotected_kuragari",
  "title": "火の守りを失った通路のくらがり",
  "watch": ["enter", "move", "light", "object", "state"],
  "repeat": "change",
  "condition": {"op": "not", "arg": {"ref": "field.environment.fires.protected"}},
  "action": {"type": "battle", "encounter": "kuragari_hunt"},
  "message": "火の守りが届かない。くらがりが通路から襲いかかる。"
}
```

`watch` は関係する変更の通知を指定する。`enter` は進入・転送・階段到着、`move` は歩行完了、`light` は歩行による燃焼や灯火・照度に関わる変更、`object` は装置操作・配置物の状態変更、`state` はフラグ・変数・物語行為・所持品などを変更する命令を対象とする。購読は現在の迷宮と通知種別で索引化し、同じ候補への複数通知は保留中に1件へまとめる。描画・向き変更・操作画面の開閉・取消では通知しない。毎フレームの走査はしない。新しい値の変更経路を追加するときは、その経路から対応する通知を発行する。

条件は既存の式記法を使う。`field.cell` は現在のセルレイヤー、`field.cell.parameters` は局所パラメータ、`field.illumination` は光源・遮蔽・局所照度を合成した0〜8の明るさ。`field.environment.<system ID>` は固有システムが提供する値で、firesはprotected・sources・rate・enemyScale・fuelを公開する。照度と環境値は条件が参照したときにだけ計算する。任意の `points` でmap/x/y/zが一致する占有セルへ限定できる。別マップ・別迷宮の通知は持ち越さない。

`repeat` は `once`（その迷宮定義のIDでゲーム中1回）、`entry`（同じセル入場で1回）、`change`（新しい購読通知で再評価）。成立前に実行済みにはしない。発火時には実行済み記録と回数を先に保存する。会話・戦闘・未完了命令がある間は候補IDを保留し、再開時に最新の条件を定義順で評価する。保留先の迷宮・探索番号、候補、入場内の実行済みID、イベント回数を保存・検査する。状態を再び変えるイベント連鎖には既存の実行上限を適用する。

成立時は `action: {"type":"battle","encounter":"遭遇ID"}` または `action: {"type":"script","script":"スクリプトID"}`。会話、分岐、戦闘後の処理が必要ならscriptを使う。戦闘中の台詞や結果の継続は既存のbattle.start命令が管理する。

どの経路で戦闘が始まっても、その時点で保留していた環境由来のbattle候補を消費する。同じ歩行・消灯から、既存の物語戦闘と通常襲撃を連続して発生させない。script候補は保持する。逃走・勝利・画面の再描画だけでは通常襲撃は再発せず、次の歩行・灯火などの通知で再判定する。戦闘中に別の変更通知が発行された場合は終了後の最新状態で評価する。

くらがりの条件は照度0ではなく魔除けの保護がないこと。普通の火は明るくても襲撃を防がない。q001の消灯・新人登場・強制終了・現地救助のスクリプトは維持し、通常襲撃と二重発火しない。火の部品は保護状態などを提供し、襲撃の発火・再発・開始は共通側で管理する。fire設定のthreatは撃退技能の対象照合と無報酬の検査に残る。

目的地到着はすでに共通処理のarriveEventで確定する。任意の物語行為ごとの到着効果と町到着も扱うため、迷宮限定のfieldEventsへ再登録しない。クエストautoは受注中クエストのautoだけを候補にし、既存の条件・一回性を保持する。

動力装置の守護者と空気供給の全滅救助は専用処理を維持する。守護者は系統操作・部品接続・戦闘中の装置ID・勝利時の稼働状態が一体で、汎用式へ分解すると同じ状態遷移を二重管理する。空気供給の救助はHP更新直後の全滅処理であり、条件付き戦闘ではない。水位・腐食・地形変更・通常ランダム遭遇も各部品の更新順・乱数を維持する。専用フックを増やす前に、この例外理由が当てはまるか確認する。

## 物語の移動

`story.journey` は出発準備を確定して会話を閉じる。到着効果・情報取得・同行者の到着は、目的地のセルを実際に踏むか、目的地の町施設へ入った時に自動確定する。途中の正面セルから到着を成立させない。

上部の「次の目的地／目的地で続きを進める」帯と `journey.arrive` のUI操作は削除した。目的地は手帳・メインクエスト欄で案内する。クエストの「迷宮の入口へ向かう（ダンジョン名）」は町の施設からその迷宮の入口へ移動する。入口からイベントセルへは探索して到達する。

## 戦闘イベント

`battle.start` は指定encounterで強制戦闘を開始し、現在のフィールド命令位置を保持する。戦闘内の `events` はID、`triggers`、任意の `condition`、`commands` を持つ。`src/core/battle-events.js` に登録した判定時点を、実装・検査・JSONスキーマで共有する。

1. `start`：戦闘開始時。
2. `round_start`：敵の行動終了後、次のラウンド開始時。最初は第2ラウンド。
3. `before_end`：勝利・敗北・逃走・撃退の結果確定前。`battle.pendingResult` で結果を判定できる。

条件成立した未実行IDを定義順に開始する。1戦中の各IDは一度限り。台詞や選択中は戦闘操作と他のフィールドイベントを止める。イベント終了後は同じ判定時点の残りのイベント、戦闘再開または保留結果の確定へ進む。

`battle.end` はイベントから戦闘を強制終了し、`on_interrupt` へ進む。中断回数を記録し、勝利報酬・勝利回数・逃走回数は追加しない。通常の終了先は `on_win`・`on_lose`・`on_escape`。戦闘イベントで許可する命令は検査器が限定し、戦闘の重複開始や勝手な町移動を防ぐ。

戦闘中の実行済みID、現在のイベント、判定時点、命令位置、終了待ち結果を保存する。q001の `q001-B-rookie` は第1ラウンド後の新人の台詞から救助行為、強制終了、現地の救助会話へ接続する。早期勝利・逃走・撃退でも新人イベントを通し、救助前の全滅では油を消費せず再挑戦できる。

## 条件自動イベントの例

次はクエストq021の原稿へ追加する場合の記法例。現在の配布シナリオにこの例自体は登録していない。

```json
{
  "id": "sealed_gate_opened",
  "title": "封印解除後の異変",
  "trigger": "auto",
  "once": true,
  "dungeon": "region_2",
  "points": [],
  "condition": {"op": "eq", "left": {"ref": "flags.sealedGateOpen"}, "right": true},
  "script": "q021.sealed_gate_opened"
}
```

同じクエストの `scripts` に `q021.sealed_gate_opened` を定義する。その命令列に会話・選択・`battle.start` を組み合わせる。
