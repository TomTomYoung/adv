複数ダンジョンと固有システムの設計仕様

2026-09-14。会話で提示し、ユーザーがdocへの格納を指示した設計です。

採用方式は「ダンジョン定義＋組合せ可能なシステム部品＋条件付きルール」です。保存はJSON、最終的な編集手段は専用フォームとし、同じ構造のYAML入出力を提供する設計です。

本書は目標仕様です。1.5.0ではダンジョン分離とfire_network、1.6.0ではwaterworks・corrosion・breakable_wallsを実装しました。全体を実装済みとは扱いません。現在使える設定と検証は [KAGARIBI_DUNGEON.md](KAGARIBI_DUNGEON.md) と [WATERWAYS_SALT_MINE.md](WATERWAYS_SALT_MINE.md) を参照してください。

1. ダンジョンを独立した設定単位にします。

地域、ダンジョン、マップを分離します。一つの地域に複数のダンジョンを置けます。一つのダンジョンのマップ数や接続順を二階層などに固定しません。

ダンジョンは識別ID、名称、説明、所属地域、入口、所属マップ、採用システム、固有状態、固有ルール、表示設定を持ちます。名称変更時もIDを維持すればセーブ・クエスト参照を維持できます。マップIDは作品全体で一意とし、一つのダンジョンに属します。

マップ内には水没区画、安全地帯、魔力封鎖区域などの区画とタグを定義します。適用範囲は全ダンジョン、特定マップ、区画、オブジェクトから選択します。同じ迷宮でも第一層は通常探索、第二層は酸素管理、祭壇の周囲だけ魔法禁止と指定できます。

2. 編集元を一本化します。

編集元は authoring/dungeons/<ID>.json です。フォームは同形式を読み書きし、YAMLは同じデータ構造に変換します。JSONとYAMLの両方を独立した正本にはしません。検証後、ゲーム用の正規化JSONとマニフェストを生成します。再生成しても作者の修正が消えないようにします。

フォームは「仕組みを追加→酸素→最大40→水没区画で時間ごとに1消費→0で救出」のように対象・条件・数値・結果を選択できます。設定から説明文も生成し、結果を確認できます。普段はフォーム、必要な場合はJSON/YAMLの直接編集を使います。

3. システムを再利用できる部品として定義します。

初期の部品群として次を設計します。

① 資源管理。灯油、酸素、体温、汚染、警戒度の初期値・上限・増減条件・閾値・表示。
② 時間と段階変化。潮汐、昼夜、機関の周期、崩落までの猶予。
③ 通行と地形変化。水位による通行可否、扉、橋、危険床、対応マップへの切替。
④ 遭遇。候補・重み・頻度・安全地帯、警戒度や時間による候補変更。
⑤ 行動と戦闘への制約。魔法の可否、追加消費、属性効果、休息・逃走条件。
⑥ 装置と連動。スイッチ、弁、祭壇から状態・扉・通路・他装置を変更。
⑦ 探索の継続。中継地点、帰還先、再入場地点、探索ごとに戻す状態。

部品は複数併用できます。酸素と水位で水没遺跡、警戒度と遭遇で潜入型の迷宮を構成できます。既存部品の組合せ・数値変更は設定だけで完結します。未対応の自動生成、敵移動AI、描画方式などの新能力には部品実装が必要です。一度追加した部品は他のダンジョンでも使えます。

コアにダンジョンID別の分岐を増やしません。部品の実装レジストリに use 名と処理を登録し、ダンジョンは use と設定だけを持ちます。排他的な地形生成・遭遇供給などの競合は検証で拒否します。

4. 個別ルールは「出来事・条件・処理」で記述します。

例えば、弁の操作と所持品条件から道具を消費して水位を下げます。勝利と警戒度条件から増援候補を変更します。特定の同行者と碑文の調査から専用シナリオを開始します。

出来事は入退場、移動成功、区画進入、装置操作、時間経過、資源変化、戦闘開始、ラウンド終了、勝利・逃走・敗北、シナリオからの通知を用意します。

条件・会話・分岐は現行の式評価とシナリオ命令を拡張して使います。所持品・仲間・フラグ・クエスト・戦績に加え、ダンジョン状態と職業・装備を反映した能力値を参照できます。任意のJavaScriptやevalは定義に含めません。

クエストからの装置操作も通常操作と同じ専用命令を通し、文章上の状態と探索マップを一致させます。作者用の真相・信念・開示順のデータは、探索のルールから自動で改変しません。

5. 時間と処理順を固定します。

移動、装置操作、道具、待機、戦闘ラウンド、シナリオ内作業の時間コストをダンジョンごとに指定します。文章の続きを読む操作、メニュー、描画、ロードで時間は進みません。長時間作業は成立時に一度だけ所定時間を加算します。

処理順は①通行・使用条件と資源の確認、②行動成立・費用・時間確定、③資源・周期・環境の更新、④閾値による救出・警報、⑤移動先のイベントと通常遭遇です。消耗の文脈は行動開始地点、進入効果は移動先とします。途中で転送・救出されたら、元の場所の遭遇を破棄します。

同時発動は処理段階・優先度・ルールIDで決定します。会話・戦闘が始まれば残処理を待機し、終了後に再開します。待機位置・処理済みIDを保存し、ロードによる費用・報酬の二重処理を防止します。数値の加算と上書きの競合を区別し、不明確な排他的上書きは検証エラーとします。イベント連鎖には実行上限を設けます。

6. 所属と保持期間を分けます。

保持期間は世界全体、ダンジョン恒久、一回の探索から選びます。世界全体は結末や町への影響、ダンジョン恒久は近道・修理済み装置、一回の探索は酸素・警戒度・今回の配置です。マップ・オブジェクト局所状態にも保持期間を指定します。

一回の探索は入場から通常帰還・緊急帰還・敗北で探索を終えるまでです。階層移動、セーブ、ロードでは初期化しません。宝箱や泉は世界で一度、探索ごとに一度、指定時間後に回復を選べます。クエスト報酬の完了管理は探索の初期化から独立させます。

地形変化は元のマップに対する差分として保存します。作品データそのものは実行時に書き換えません。状態と乱数を保存し、他の迷宮・新規ゲームに変更が混ざらないようにします。

7. 目標形式の記述例です。

以下は将来のresource・汎用rule部品の例です。1.5.0の実行データではありません。現在使える具体例は authoring/dungeons/kagaribi.json です。

```yaml
schemaVersion: 1
id: lamplighter_sewer
name: 灯守の地下水道
region: 1
profile: classic
maps:
  - region_1_f1
  - region_1_f2
entries:
  main:
    map: region_1_f1
    point: entrance
clock:
  costs:
    move: 1
    interact: 1
    item: 1
    wait: 1
    battle_round: 1
systems:
  oxygen:
    use: resource
    label: 酸素
    scope: expedition
    initial: 40
    min: 0
    max: 40
    display: gauge
    consume:
      on: exploration.tick
      amount: 1
      when:
        op: location_has_tag
        tag: underwater
rules:
  refill_oxygen:
    on:
      event: zone.entered
      tag: breathable
    do:
      - op: resource.refill
        system: oxygen
  rescue_on_depletion:
    on:
      event: resource.depleted
      system: oxygen
    do:
      - op: narrate
        text: 息が続かない。救助用の綱を引き、入口へ退避した。
      - op: dungeon.evacuate
        entry: main
        endExpedition: true
```

resource.depletedは正数から0への遷移時に一度だけ発生します。

profileは部品と標準値のまとまりです。優先順位はプリセット、ダンジョン、マップ、区画。部品とルールはID単位で上書き・無効化します。同順位の区画が矛盾する場合は読み込み順で決めず検証エラーとします。

8. 表示を採用部品に合わせます。

部品はゲージ、残り時間、現在段階、警告文、使用可能操作などの表示情報を投影します。未採用部品は表示しません。非公開の警戒度などは内部数値を渡さず、公開条件を満たす警告だけを渡します。

ビューは表示用スナップショットを描き、操作IDを返します。エンジンが実行条件を再検査します。ビューは状態、乱数、報酬、スクリプト実行を所有しません。

9. 移行と完成条件です。

現行10探索先を独立ダンジョンに移し、現在の挙動をclassicとして再現します。マップID、クエストID、記録を維持します。旧現在地から所属ダンジョンを特定し、灯油・歩数・宝箱・装置状態を引き継ぎます。

次に資源・周期・条件付き通行と遭遇を作り、酸素、騒音警戒、周期通路の三種類を設定だけで構成できることを確認し、同じ定義を扱う編集画面を用意する計画です。

参照欠落、型不正、依存不足、競合、際限のない連鎖を検出します。動的仕掛けの攻略可能性は静的検査だけで保証せず、入口からの操作手順の再生で確認します。

完成条件は、既存部品による追加でコア・ビューを変更しないこと、再生成で編集を失わないこと、固有状態と処理途中の保存を再開できることです。

1.5.0時点の実装境界

ダンジョン定義の分離、JSON編集元と再生成、部品レジストリ、入退場・歩数・危険判定・遭遇・操作・投影・保存検証の接続、fire_networkを実装しています。classicは既存探索処理を維持する互換プロファイルです。汎用プリセット継承、区画ルール、汎用イベントキュー、resource/周期部品、YAML入出力、専用編集フォームは目標仕様として残っています。

1.6.0時点の追加実装

waterworksに水位周期・装置による止水と通水、corrosionに戦闘開始時の装備補正、breakable_wallsに永続的な地形開通を実装しました。共通境界へtile/block/equipmentStats/battleStart/fieldIntentを追加しています。水位の時間は部品が管理する探索行動単位で、世界全体の時計や任意の条件付きイベントキューとは別です。汎用resource、酸素、騒音警戒、YAML、編集フォームは引き続き将来範囲です。
