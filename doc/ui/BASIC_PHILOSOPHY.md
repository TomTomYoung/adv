# UI基本哲学

制定日: 2026-09-27。最近のUI修正指示から言語化した共通方針です。新しい画面・機能の設計と、既存UIの修正判断に用います。

## 中心となる原則

プレイヤーの判断の流れと、画面上の情報・操作の流れを一致させ、その対応を操作の途中で崩さないようにします。

プレイヤーが考える対象は、探索、戦闘、購入、編成など、ゲーム内で何をするかという判断です。UIは、その判断に必要な情報を示し、対象と操作を明確に結び付け、確定した行為を意図どおりの結果へつなげます。

この文書は継続して使う設計基準です。実装状況と個別仕様は[根本方針と現在の実装](PHILOSOPHY_AND_STATUS.md)、検証済みの範囲は[検証記録](../development/PROGRESS.md)で確認します。

既存のHCI研究・設計原則との対応は[参考理論と適用例](THEORY_REFERENCES.md)を参照してください。原典の要点、advでの適用例、適用上の注意と出典をまとめています。

## 1. 画面の目的に沿って操作をまとめる

各画面に目的を定め、その目的に必要な操作を集めます。ショップでは購入、旅支度では所持品の管理、隊の状態では編成を扱います。転職や魔法使用は、それぞれ該当する人物のページへ置きます。

プレイヤーが「いま何をする場所にいるか」から、情報と操作の所在を予測できるようにします。機能が増えても画面の目的を維持し、追加する操作がどの目的に属するかを先に決めます。

## 2. 操作候補は段階に合わせて絞り、判断材料は同時に見せる

戦闘では、行動者を確認し、行動カテゴリを選び、具体的な技能や道具を選び、必要な場合だけ対象を選びます。その段階で判断する候補を順に出します。

ショップでは、商品・価格・能力値・説明・各人の装備可否・所持数を同時に確認できるようにします。購入を判断するために必要な情報は、判断が終わるまで保持します。情報を覚えて別の画面へ移る手間を減らします。

操作候補を絞ることと、判断材料を揃えることをセットで設計します。表示要素を減らす際は、その情報が現在の判断に必要かを確認します。

## 3. 選択中の対象に情報と操作を結び付ける

人物カードを選ぶと、その人物のプロフィールを表示します。隊の状態では、選択した人物に対して共通の「待機」「加入」「△」「▽」を使います。商品を選ぶと、その商品の詳細と、各人物の装備可否・所持状況を表示します。

「何について見ているか」と「誰に何をするか」を常に対応させます。対象を選び直すと、同じ領域の情報と操作がその対象に追従します。対象の数が増えても、選択と操作の関係を維持します。

並べ替えや購入などの操作後も、引き続き同じ対象を扱う場合は、その選択と詳細表示を保持します。

## 4. 覚えた操作と画面上の位置を継続して使えるようにする

決定・キャンセル・方向入力の共通化、選択肢へのフォーカス、キャンセルで一段ずつ戻る経路、固定したメッセージ領域を維持します。情報量や候補数が増えた場合は、担当する領域の中でページ送り・スクロールを行います。

ダンジョンでは方向入力で直接移動し、選択画面が開いている間はその画面の候補を選びます。現在の操作範囲を明確にし、選択中に背後の探索が動かないようにします。取消後は、元の対象や探索へ理解できる順序で戻します。

移動の「前へ」を押していた場所にイベントの「続きを読む」が現れると、プレイヤーの意図が変わっていないのに、継続中のクリックの意味だけが変わります。このような遷移では、移動領域を同じ位置に残して無効化し、会話送り・選択肢を別の担当領域へ置きます。

探索から戦闘へ移る場合は、移動を押していた位置に行動者などの見出し領域を置き、戦闘行為を誤って選ばないようにします。戦闘内の「攻撃→対象選択」は同じ意図を続ける操作として、見出し行を揃えて攻撃と先頭対象を同じ位置に置きます。意図が切り替わる境界と、一つの行為を続ける手順を区別して配置します。

操作できない領域にも「ここは移動を扱う場所である」という役割があります。状態変化に合わせて有効・無効や内容を切り替えても、覚えた配置と操作の対応を壊さないようにします。これは操作領域の役割を保つ基準であり、画面サイズに応じた配置調整は[表示仕様](IN_SCENE_VIEW.md)に従います。

## 5. ゲーム内の結果を、実際に確定した行為に対応させる

候補の閲覧や対象の選択中は、購入・資源消費・戦闘行動を確定しません。確定操作が行われた時点で、現在の条件を検査して実行します。取消は定義された前の段階へ戻り、未確定の行為を実行しません。

到着イベントは実際に現地へ到着したことで成立させます。資材不足には、その不足に対応する退出・再開の経路を用意します。表示される行為、プレイヤーの選択、ゲーム内で起きる結果を一致させます。

「目的地で続きを進める」や共通の「中断し、同じ場面から再開する」のような内部進行の操作を追加する前に、プレイヤーがゲーム内で何を行うのかを定義します。場所への到達、会話、退出、補給後の再訪など、その行為と成立条件をUIへ対応させます。

## 画面を定義する六つの要素

各画面は次の六つで定義します。

1. 現在の目的。探索、購入、編成、技能の使用など、この画面で何を行うのかを定めます。
2. 選択中の対象。人物、商品、技能、敵など、表示と操作が何に属しているかを定めます。
3. 判断の段階。カテゴリ選択、具体的な行為の選択、対象選択、確定など、いま決める内容を定めます。
4. 必要な情報。その判断に必要な説明・数値・費用・可否・結果の見込みを定めます。
5. 実行できる操作。現在の段階で選べる行為と、有効・無効の条件を定めます。
6. 確定・取消の行き先。何を確定するとゲーム状態が変わり、何を取り消すとどの段階・対象へ戻るかを定めます。

六つの要素を定めたうえで、表示領域・操作領域・フォーカス・キー割り当てを設計します。

例えばショップの商品選択では、目的は購入、対象は選択商品、判断段階は商品と購入先の検討です。必要な情報は価格・性能・説明・所持金・人物ごとの装備可否と所持数です。購入先の確定で支払いと品物の受領が成立し、購入先選択の取消では選択商品へ戻ります。

## 画面遷移で守る条件

1. 選択対象と、表示される情報・実行する操作の対応を保ちます。
2. 現在の判断に必要な情報を見える状態に保ちます。
3. 継続して使う操作領域の役割と位置を保ちます。
4. 前の操作の続きが、別の行為を勝手に確定しないようにします。
5. 取消によって、理解できる段階と操作位置へ戻れるようにします。

静止した一画面に加えて、対象を選び直す、選択肢が現れる、イベントが始まる、処理が終わる、一覧が増える、といった変化の前後を確認します。

## UI変更時の使い方

新しい機能を配置する前に、「プレイヤーはいま何を判断していて、その判断に何が必要で、どの操作で確定するのか」を定めます。配置・表示量・階層・フォーカス・無効化は、その回答に沿って決めます。

実装後は、対象と情報の対応、確定前の無消費、取消先、イベント境界での入力、固定領域のスクロールを確認します。画面座標・重なり・クリック可能範囲を変更した場合は実ブラウザでも確認し、DOM上の検査と区別して記録します。
