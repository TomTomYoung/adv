
## 実装時に維持すること

Coreはゲーム状態を所有し、ApplicationはコピーしたViewModelを作り、Viewは表示とdispatchだけを行います。固有の依頼IDを共通コアへ追加せず、条件・本文・分岐を原稿へ置きます。

技能は `engine.skills` と許可計画器で判定します。人物定義の旧 `skills` 配列だけで使用可否を決めません。派生能力は `actorStats`、環境による制限はダンジョンのフックを通します。テストのレベル変更も `award` を使い、成長履歴との整合を保ちます。

失敗した操作でMP・材料だけを先に失わせないでください。戦闘後の作業は勝利時だけ確定し、逃走・敗北・中断で未成立の救助や合意を追加しません。乱数は保存されたPRNGを使います。

旧script ID・配列順・分岐path・呼出scopeを保持します。`legacyQuestRoutes`、`legacyStoryRoutes`、`catalogRevision`、q008の状態改訂を混同しません。現地調査の会話構造を変える場合は原稿の revision を上げ、旧版を残します。

## 次に残る作業

### クエスト固有イベント定義をすべてクエストJSONへ集約する

クエストに属する情報は、原則として対応する `qXXX` の原稿・クエストJSONを正本にする。現在 `dungeons[].fieldScenes`、`authoring/dungeon-scenes.json`、各 `data/maps/*.json` のクエスト専用objectなどへ分散しているクエスト固有データを、すべてクエスト側へ寄せる。

移行対象には少なくとも、イベントオブジェクトの配置先map・座標・object ID・kind・trigger・safe・once・blocking・initialState・script、イベントオブジェクト自体の出現条件・有効条件、会話や文章の表示条件、選択肢の `visibleWhen`、選択可否の `condition`、選択肢本文・要求表示・commands、分岐、戦闘、報酬、物語状態、クエスト固有の関連ダンジョン・調査地点・調査条件・調査script・noteを含める。つまり「イベントがいつ出るか」「調べられるか」「中で何を話すか」「どの選択肢が見えるか」「どれを選べるか」「選択後に何が出現・消滅するか」までクエストJSONで完結して記述できる形にする。

マップ定義側には地形、入口、階段、汎用の宝箱・泉・罠・扉など、そのマップ自体に属する要素だけを残す。クエスト専用objectはクエストJSON側からmap・座標を参照して投影・実体化する方式へ変更する。ダンジョン定義側には `maps`、`systems`、`art`、入口など、そのダンジョン自体の構造と固有システムだけを残し、ダンジョン側からクエストを逆参照する構造を廃止する。

`fieldScenes` という独立概念は廃止を前提に棚卸しし、単なるクエスト内イベントとして表現する。現行13件の `fieldScenes` はすべて対応するクエストへ移す。`projectFieldLinks`、`projectFieldNotes`、`dungeonScenePlan`、関連検証、UIの「現地調査へ向かう」もクエスト側定義を読む構造へ変更するか、不要なら整理する。

移行時は現行のscript ID、object ID、イベント済み状態、調査済み状態、旧セーブ互換を壊さないこと。旧 `legacyQuestRoutes` / `legacyStoryRoutes` で必要なmap objectは互換層として残してもよいが、通常経路の正本はクエストJSONへ一本化する。移行後は「クエストJSONだけを読めば、そのクエスト固有の配置・出現条件・会話・選択肢・分岐・状態・結末まで追える」ことを検証条件にする。

### q001「帰らない灯番」を火と恐怖を軸に改稿する

q001 は次回改稿で、入口から老人のいる地点までの一部区間について、壁の松明が油切れで消えている状況を物語とゲーム状態の双方に組み込む。プレイヤーは通常所持している松明で暗区間を進み、老人を発見して一緒に入口へ戻る流れを基本骨格とする。

新人は老人から油を渡されて入口までは戻れているが、暗闇への恐怖によってクライマックスまで入口から動けない。現行の `rookie_together` のように新人がプレイヤーと支道へ同行する通常ルートは、この新しい人物設定と矛盾するため改稿対象とする。

シナリオ開始直後、入口にいる新人との会話で、この迷宮における松明と火の基本ルールを必ずプレイヤーへ説明する。壁の松明と携行松明が安全確保に使われること、火を絶やすと「暗がり」が寄ってきて襲うことを、後から都合よく判明する設定ではなく、探索前に知っている危険として提示する。新人自身がそのルールを理解しているからこそ、入口から先へ戻れず恐怖していることも会話上で伝える。

入口から老人の待機地点までの油切れ区間には、消えている壁松明を調べるイベントを置く。プレイヤーが点灯を試みた場合は、芯や点火操作の失敗ではなく、壁松明側の油が完全に切れているため火がつかないことを明示するテキストを返す。必要なら複数の壁松明に同様の状態を持たせ、油切れ区間そのものをプレイヤーが実地に確認できるようにする。

老人の待機地点には、まだ点いているが油が残り少ない壁松明を置く。この火が老人をその場に留めている最後の安全圏であることを示す。残油がもうすぐ尽きることは、壁松明を調べた際のテキスト、老人との会話、またはその両方で確認できるようにする。老人が無意味にその場で待っているのではなく、「この火が消える前に誰かが来ることを待っている」という状況が分かるようにする。

帰路の暗区間でプレイヤー側の松明が消れ、火を避けていた「暗がり」が襲来する。暗がりは序盤から火の外側で気配を見せるなど、火がある間は寄れず、完全な暗闇で襲う存在であることを事前に示す。唐突な襲撃にしない。最初の新人による説明、油切れ壁松明、老人地点の残り少ない壁松明、帰路での消灯、暗がりの襲来が一本のルールでつながるようにする。

クライマックスでは、入口で恐怖のため動けなかった新人が、恐怖を克服して平気になるのではなく、恐怖を抱えたまま老人とプレイヤーを助けるため自分の意思で暗区間へ踏み込む。新人は老人から受け取った油で灯した松明を持って駆けつけ、その火で暗がりを退ける。老人が先に自分の油で新人を救い、その同じ火が最後に新人から老人へ返される往復構造をq001の中心モチーフとする。

状態設計では「恐怖が消えた」ことを成立条件にしない。新人の恐怖は残ったままでもよく、「恐怖があるにもかかわらず助けに動いた」という行為を別状態・行動履歴として表現する。必要なら `entry` と `branch` の間に暗区間を物語上の場所として追加し、松明の点灯状態、壁灯の消灯、壁灯の残油、暗がりの出現・退去、新人の所在地、老人の所在地をシナリオJSONの状態とイベント条件で追跡できるようにする。

この改稿では、既存の `informed` / `contract` / `compromise` を機械的に維持せず、新しい中心骨格を損なわない形で結末・分岐を再検討する。特に、クライマックス以前に救助隊へ丸投げして新人の決断を一切見ずに終われる分岐が物語の核を壊さないか確認する。作者向け `model.world`、agents の goal、reveal、graph、`story.registry`、`story.actions`、`story.endings`、`scripts.q001.v11.*`、マップ上のクエストイベント配置まで一貫して更新する。

HTTP経由での起動から、選択・中断再開・帰還・保存再読込までの操作を確認します。スマートフォン幅、画像ロード失敗、BGMとSEの聴感も対象です。

全文監査では人物の目的、得た情報、行為、応答、代償を具体的な選択列で確認します。到達テストの成功を、全200本の文芸的な分化の証明としません。

現地調査は観察を記録する段階です。固有の装置を本筋の救助・搬送・合意・結末へさらに接続する際は、その事実に対応する条件と互換性を原稿側で定義します。

汎用Objective／Reward／Counter、一般シナリオからの最終能力参照、世界共通の時計・NPCスケジュールは未実装です。既にある戦績やq001〜q010の型付き物語状態を再実装する前提で計画しないでください。

文書の古い設計・測定値は [legacy](legacy/README.md) に日付付きで保持しています。現行文書を旧版の記述へ戻さず、コードと配布JSONを照合して更新します。
