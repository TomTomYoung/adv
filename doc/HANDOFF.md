## 生成と検証

```sh
npm run build:scenarios
npm run check:docs
npm run check
```

全生成はbuild:catalogとbuild:docsまで含みます。表示例を変更したら `node tools/build-fixtures.mjs` で11個の現行スナップショットも更新します。配布JSONからカタログだけを更新する場合は `npm run build:catalog`、ダンジョンのみは `npm run build:dungeons`、職業は `npm run build:jobs`、人物は `npm run build:characters` を使います。エディター用スキーマは `node tools/build-schemas.mjs` です。文書の説明だけを修正した場合は全生成せず、`npm run check:docs` と差分確認を行います。集計文書の更新が必要な場合は `npm run build:docs` を使います。

PR #15では全生成を再実行し、data・doc計309ファイルのハッシュが一致しました。今後も生成前後の差分を確認し、配布JSONだけの手修正や、利用者が加えた原稿の上書きを避けてください。

`node tools/build-fixtures.mjs` は data/view-fixtures.json の画面プレビュー用スナップショットを再生成します。文書だけの修正では実行不要です。旧セーブのテストfixtureはこれとは別に保持し、旧版を読み込んだ際に新規開始へ切り替える検証資料として扱います。

## 実装時に維持すること

Coreはゲーム状態を所有し、ApplicationはコピーしたViewModelを作り、Viewは表示とdispatchだけを行います。固有の依頼IDを共通コアへ追加せず、条件・本文・分岐を原稿へ置きます。

技能は `engine.skills` と許可計画器で判定します。人物定義の旧 `skills` 配列だけで使用可否を決めません。派生能力は `actorStats`、環境による制限はダンジョンのフックを通します。テストのレベル変更も `award` を使い、成長履歴との整合を保ちます。

失敗した操作でMP・材料だけを先に失わせないでください。戦闘後の作業は勝利時だけ確定し、逃走・敗北・中断で未成立の救助や合意を追加しません。乱数は保存されたPRNGを使います。

利用者の指定により現行1.11.0も旧内容版のセーブ移行を行いません。読込エラーは最初から開始します。同版の正常な保存は継続できるよう、命令配列を構造変更する際は内容版を更新します。現地調査の改稿は原稿の revision を上げます。
