## 生成と検証

```sh
npm run build:scenarios
npm run check:docs
npm run check
```

全生成はbuild:catalogとbuild:docsまで含みます。配布JSONからカタログだけを更新する場合は `npm run build:catalog`、ダンジョンのみは `npm run build:dungeons`、職業は `npm run build:jobs`、人物は `npm run build:characters` を使います。エディター用スキーマは `node tools/build-schemas.mjs` です。文書の説明だけを修正した場合は全生成せず、`npm run check:docs` と差分確認を行います。集計文書の更新が必要な場合は `npm run build:docs` を使います。

PR #15では全生成を再実行し、data・doc計309ファイルのハッシュが一致しました。今後も生成前後の差分を確認し、配布JSONだけの手修正や、利用者が加えた原稿の上書きを避けてください。

`node tools/build-fixtures.mjs` は data/view-fixtures.json の画面プレビュー用スナップショットを再生成します。文書だけの修正では実行不要です。旧セーブのテストfixtureはこれとは別に保持し、旧版を読み込んだ際に新規開始へ切り替える検証資料として扱います。

## 実装時に維持すること

Coreはゲーム状態を所有し、ApplicationはコピーしたViewModelを作り、Viewは表示とdispatchだけを行います。固有の依頼IDを共通コアへ追加せず、条件・本文・分岐を原稿へ置きます。

技能は `engine.skills` と許可計画器で判定します。人物定義の旧 `skills` 配列だけで使用可否を決めません。派生能力は `actorStats`、環境による制限はダンジョンのフックを通します。テストのレベル変更も `award` を使い、成長履歴との整合を保ちます。

失敗した操作でMP・材料だけを先に失わせないでください。戦闘後の作業は勝利時だけ確定し、逃走・敗北・中断で未成立の救助や合意を追加しません。乱数は保存されたPRNGを使います。

利用者の指定により1.9.0は旧内容版のセーブ移行を行いません。読込エラーは最初から開始します。同版の正常な保存は継続できるよう、命令配列を構造変更する際は内容版を更新します。現地調査の改稿は原稿の revision を上げます。

### q001「帰らない灯番」の火と恐怖

1.9.0の改稿は実装済みです。現行は7場面、物語状態の改訂2、救助後の2結末です。全文と分岐は[カタログのq001](QUEST_CATALOG.md#q001-帰らない灯番)、仕様と保存時の挙動は[改訂概要](DUNGEON_REVISION_1_9.md)にあります。

入口で新人から火のルールを聞き、油切れの壁灯を確認し、最後の弱い火の下の老人を介助します。帰路で火が消え、火の外にいたくらがりが迫り、新人が老人から受け取った油の火で二人を救います。新人は救助前まで入口に留まり、恐怖が消えたことを救助の条件にしません。恐怖と救助行動を別状態として維持してください。

壁灯3本は `state.objects` と `object.state.set` で個別管理します。油切れは `empty`、老人地点は `low`、帰路の消灯後は `extinguished` です。壁灯の状態をクエストフラグへ複製せず、携行火、人物・油の所在、実マップの座標と整合させます。壁灯の歩数ごとの数値燃料管理は未実装です。

結末は `informed`（巡灯路の修繕）と `compromise`（二人の付き添い）です。旧3結末や新人同行の経路を復活させず、どちらも新人の救助を経て選びます。

## 次にやること（最優先）: 町ロケーション・ダンジョン・シナリオ配置を一つの世界構造として接続する

現状ではダンジョンID・名称・所属マップとクエストイベント配置が既に存在します。一方、町の共通ロケーションツリーとq002の施設間の実移動は未実装で、`school`・`office` はクエスト内の物語上の場所です。既存の定義と検証を拡張し、場所の正本を二重化しないでください。以下の要件本文を次工程へ引き継ぎます。

町には、ダンジョンのセル移動とは別に、選択肢によってツリー状に移動できる共通ロケーション系を実装する。町を根または上位ノードとし、店、宿屋、ギルド、医学校、医学校の標本室、保険審査所などを、クエスト固有の論理上の場所ではなく、複数シナリオから参照可能なワールド側のロケーションとして定義できるようにする。親子関係または遷移先をデータで持ち、町の画面から選択肢で施設へ入り、施設内でさらに部屋や窓口へ進み、適切な戻り先へ戻れるようにする。

一枚絵ロケーションの表示は、背景一枚絵を基礎に、その上へ登場人物のスプライトを重ね、テキストウィンドウと選択肢で会話・調査・取引・宿泊・シナリオ進行が成立する構成とする。店や宿屋もこのロケーション方式に含め、専用の別UIへ閉じ込める必要がある機能だけを追加パネルとして扱う。Coreが場所・人物・会話状態を所有し、Viewは背景・人物スプライト・テキストウィンドウを描画するという既存の責務分離を維持する。

ロケーションには安定したIDと名称を与え、シナリオ側は表示名の文字列ではなくロケーションIDを参照する。クエスト内だけの `school` や `office` のような仮想場所で完結させず、共通施設として存在すべき場所はワールドロケーションへ昇格させる。q002「骨の荷札」の医学校の標本室と保険審査所は、この方式へ移す最初の確認対象とする。物語状態の `partyAt`、人物や物品の所在、知識取得条件は、実際のロケーション遷移と矛盾しないように接続する。

各一枚絵ロケーションは背景アセットと、必要に応じて人物スプライトの配置情報を参照する。既存素材が不足している場合は、その場しのぎのプレースホルダーで終わらせず、必要な背景一枚絵・人物スプライト・関連表示素材を生成してリポジトリへ配置し、`data/assets.json` と `assets/PROVENANCE.md` を含む現行の素材管理へ登録する。生成素材は現在のゲームの画面構成・色調・解像度に合わせ、会話時に人物が背景へ自然に重なることを実画面で確認する。

ダンジョンには、表示名だけではなく安定したダンジョンIDと名称を必ず持たせる。フロアや実マップはダンジョンIDへ所属させ、シナリオから「どのダンジョンの、どのマップ・階層・座標・オブジェクトで起きるイベントか」を機械的に参照できるようにする。既存の `region_N_fM` のようなマップIDだけで意味を推測させず、ダンジョンカタログと実データの双方からIDと名称の対応を追える状態にする。

シナリオイベントは、ダンジョン内で起きるものについては実際にそのダンジョンの実マップへ配置する。本文上だけ「○○ダンジョンへ行った」と扱ったり、別のダンジョン上の便宜的なイベント座標から会話だけで目的地へ飛ばしたりしない。クエスト固有イベントは引き続きクエストJSON側を正本としてよいが、その `map`、座標、object/event ID は対象ダンジョンの実在するマップと一致させ、現地へ到達して調査・会話・戦闘・回収を行う構造にする。

一つのシナリオは、ダンジョンと一枚絵ロケーションの双方をまたいでよい。たとえば町の依頼人との会話、ダンジョンでの現地調査、医学校の標本室での照会、別施設での審査という流れを、一つのシナリオ進行として連続して扱えることを前提にする。場所をまたぐ際に物語状態だけを書き換えるのではなく、実際の現在地種別と現在地IDも整合させる。

`doc/QUEST_CATALOG.md` は、この場所構造を作者と実装者が追跡できる索引として更新する。各シナリオについて、関係するダンジョンはダンジョンID・名称・必要ならフロア／map ID・座標・イベントIDを記載し、一枚絵ロケーションはロケーションID・名称を記載する。進行が複数地点をまたぐ場合は、場面ごとに現在地を明示し、ダンジョンカタログおよびロケーション定義へ容易に辿れるようにする。カタログの場所情報は自由記述だけにせず、配布JSONの参照から生成または検証できる構造を優先する。

この改修では、ダンジョンID／名称、ロケーションID／名称、シナリオイベントの実配置、シナリオカタログの場所参照が相互に不一致にならない検証を追加する。最低限、存在しないダンジョンID、存在しないロケーションID、対象ダンジョンに属さないmap ID、通行不能セルや範囲外座標へのイベント配置、カタログと配布JSONの参照ずれを `npm run check` または文書検証で検出できるようにする。
