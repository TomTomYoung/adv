# マップのセルレイヤー・境界・方向別通行仕様

確認日: 2026-09-23。作品版1.16.0。通常ロードは33件すべて2Dのセルレイヤー方式です。マップ間の水密扉・階段・給排水は [CONNECTED_2D_MAPS.md](CONNECTED_2D_MAPS.md)、セル種と編集形式は [CELL_LAYERS.md](CELL_LAYERS.md) を正本とします。後半の六面・立体に関する記述は退避実装の保守仕様です。

## 1. セル・レイヤー・配置物・境界

セルは座標を持つ区画です。通行可否、テクスチャまたは画像、表示形状、遮光、フィールドイベント、照度などの値を独立したレイヤーとして持ちます。セル種は頻出する構成のプリセットであり、一地点の例外は個別上書きします。

`.` は通行可候補、`#` は通行不可だけを意味します。床・壁の見た目、水が入れるか、光が通るかを記号から推測しません。見た目が石床でも通行不可にでき、通行できる場所に遮光表現を設けることもできます。素材画像を変更しても通行判定は変わりません。

宝箱・人物・火台・レバーはオブジェクトとしてセル種から分離します。境界はセル間の継ぎ目で、2Dは辺、3Dは面です。扉・水門・壁面は境界側の定義に属します。現在の2Dマップ間接続の扉は `map_connections` の端点・方向で管理し、セル内の古い `map.objects` の扉も保守対象です。エッジ上のたいまつ・調査物体は設置セルとedge方向で配置できます。[調査仕様](ui/INSPECTION.md)を参照してください。一般の2D内部エッジの方向別通行・遮光は後続作業です。

## 2. 座標と方向

x・yは0始まりの整数です。東はx+1、西はx-1、南はy+1、北はy-1です。通常2Dはz=0、退避3Dは上がz+1、下がz-1です。斜めに接するセルへ通常移動はできません。マップの `floor` は階層の分類番号で、描画用の床やz座標とは別です。

方角は `north`、`east`、`south`、`west`、退避3Dの上下は `up`、`down` です。西隣から東へ歩いて対象セルへ入った場合、そのセルへの進入側は西です。移動方向と進入側を混同しません。`facing` は視線の方向で、後退もあるため進入側とは一致しません。

## 3. 2Dセルマップの現行仕様

### 3.1 配置と上書き

[authoring/cell-layers.json](../authoring/cell-layers.json) の `presets` がセル種、`maps` が配置です。`legend` の文字から `rows` の各地点にプリセットを割り当て、`overrides` で項目を上書きします。`visual` と `parameters` は項目単位、`events` は配列全体を置き換えます。幅・高さは全行で一致させ、範囲外は進入不可です。

生成した `map.cells` がレイヤー配置、`map.tiles` が通行値だけの投影です。ロード時に両者の一致を検査します。例えば次の通行投影の中央 `(2,2)` は進入不可ですが、その画像や遮光属性はこの文字列からは決まりません。

```json
{"tiles": ["#####", "#...#", "#.#.#", "#...#", "#####"]}
```

状態変化時は、地形パッチの `tile` と `layers`、または破壊壁の `openedLayers` を使用します。`dungeonTile` は通行値、`dungeonCell` は表示・環境値・イベント参照を解決します。植物の採取や動力停止などでパッチを解除すると元のプリセットと地点上書きへ戻ります。複数部品が同じ項目を上書きすると定義順の後の値が優先されます。

### 3.2 四方からの進入と退出

同じマップ内の通常移動は東西南北の隣接セルへ行います。現行2Dは入口の方角を記憶して出口を制限する方式ではありません。通行可候補のセルは四方からの進入・退出候補となり、四方16組に固有の制限はありません。ただし毎回、移動先・閉じた扉・水没などの条件を検査します。通行不可のセルはどの方向からも入れません。

マップ間の扉・階段は接続定義を経由します。マップ内部のセル型扉は1セル全体の占有を妨げ、独立した一方向の境界にはなりません。

### 3.3 一歩とイベントの成立条件

探索中で会話・戦闘待ちではなく、移動先が範囲内・z=0・通行値 `.`・環境による拒否なし・閉じた遮断オブジェクトなしなら移動可能です。画像や `visual.floor` は歩行可否を決めません。現在の2Dは立体的な足場計算を持ちません。

実際の到着後にセル進入を記録します。フィールド処理はオブジェクト進入、旅程到着、セルイベント、クエスト条件イベントの順です。セル種にHP減算を直書きせず、参照されたイベントのスクリプトがHPなどを変更します。一回性、再入場、保存再開の仕様は [CELL_LAYERS.md](CELL_LAYERS.md) を参照してください。

## 4. 退避した3D立方体マップの保持仕様

### 4.1 空間の配置

`map.voxels` があるマップを3D方式として扱います。`voxels.version` は1、`minZ` は最下層のz、`layers` は低いzから順番に並ぶ平面図です。`layers[z-minZ][y][x]` の `.` が空、`#` が密です。各層は同じ幅と行数を持ち、`tiles` はz=0の断面と一致させます。

現行の[貯水立坑](../authoring/voxel-content.json)はz=-1、0、1の3層です。`faces` に共有面、`links` に経路、`devices` に給水・掘削装置、`initialWater` に初期水没操作を定義します。これらの配列は空でも必要です。

密の立方体には六方向のどこからも入れず、その中を通る入口・出口の36組もすべて不可です。上面は上の空セルの床になり、側面は隣の空セルから見た壁、下面は下の空セルから見た天井になります。許可された掘削で密から空へ変えられます。

空の立方体には東西南北上下の六面があります。ただし、六面を持つことと六方向に自由歩行できることは別です。通常歩行は同じzの四方向だけです。上・下を含む移動には具体的な移動経路が必要です。空セル内部の入口・出口36組を個別に制限するデータは現在ありません。

### 4.2 共有境界面

隣接するAとBは一つの面を共有します。Aの東面はBの西面と同じ面です。Aの上面はBの下面と同じ面です。宣言は片側から一度だけ行い、両側からの二重定義は検証エラーになります。

面の `at` は基準セルA、`side` はAから見た隣接方向です。`id`、`name`、`operable`、`initiallyOpen`、`closed`、`open` を持ち、操作可能な面には空セル上の `handle` が必要です。開閉状態は両側で共有します。

各状態で独立して指定する値は次の三つです。

1. `passage`：キャラクターがその面を横切れるか。現行は一つの真偽値で、AからBとBからAに同じ値を使います。
2. `water`：その面を水が通れるか。人物の通行とは独立し、両方向で同じ値です。
3. `support`：その面が足場を支持するか。実際の足場判定では現在セルの下面を調べます。横の面に支持を指定しても床の代わりにはなりません。

未定義の面は `passage: true`、`water: true`、`support: false` として扱います。相手セルが密・範囲外なら人物は入れません。密セルは通水も遮ります。範囲外への通水可能な面は排水口になります。

`closed` / `open` は状態名です。「開いているから人も水も通る」と推測せず、その状態の三つの値を使います。例えば排水蓋は、開くと水だけ通し、人物の通行は引き続き拒否できます。

次は `voxels.faces` に置ける形の固定境界壁の例です。A=`(1,1,0)` と、その東のB=`(2,1,0)` がともに空である配置を想定しています。AからB、BからAの両方を遮断します。

```json
{
  "id": "partition",
  "name": "区画の仕切り壁",
  "at": {"x": 1, "y": 1, "z": 0},
  "side": "east",
  "operable": false,
  "initiallyOpen": false,
  "closed": {"passage": false, "water": false, "support": false},
  "open": {"passage": false, "water": false, "support": false}
}
```

固定格子なら人物を遮り、水を通すように設定できます。床板なら下面に支持を与え、水や上下通過の可否を別々に指定できます。六面のそれぞれに設定できますが、一枚の面を横切る向きはAからBとBからAの二つです。面の中へ入って北側から東側へ曲がる、といった経路は境界面にはありません。

### 4.3 通常歩行と経路移動

同じzの通常歩行では、移動先が空で、完全水没しておらず、下に密セルまたは支持面があり、二つのセルの共有面が通行可能で、移動先に閉じた遮断オブジェクトがないことを確認します。`walkable` は移動先を占有できるかを調べる関数です。出発点との境界を含む移動全体の可否は `move` などで追加判定します。

梯子・階段・ツタ・縄・橋は、`voxels.links` の `path` に空セルの座標列を記述します。各区間は六方向のいずれかに1セルだけ隣接する必要があります。斜め、密セル、閉じた面、完全水没セルを飛ばして渡れません。経路途中の足場は不要ですが、到着先には足場が必要です。橋の支持面と経路は別の定義で、`kind: "bridge"` だけでは床は生成されません。

`bidirectional: true` は `path` の順方向と逆方向の双方を利用可能にします。`false` は先頭から末尾への利用だけを許します。逆向きに通れる別経路や通常歩行まで禁止するものではありません。片方向経路の形式は実装済みですが、現在配置されている貯水立坑の3経路はすべて往復可能です。

`access.kind` は `fixed`（常設）、`install`（指定素材を消費して設置）、`skill`（指定技能で利用）です。設置や技能によって、密・閉じた面・完全水没の禁止を無視できるわけではありません。上へ登る場合も下りる場合も手段が必要です。自由落下や任意の壁越えは実装していません。

## 5. 方向別制限の拡張仕様

この節は、ユーザーが指定した「どちらからどちらへ入れるか」を表せるようにするための仕様です。入口依存のセル内通行、一方向だけ通す境界、2Dの独立した境界は未実装です。以下の記法は設計例であり、現在のSchemaは受理しません。実装時には版を追加し、既存マップの省略時の挙動を保持します。

### 5.1 セルへの進入・退出と、内部の接続

方向集合は2Dが四方、3Dが六方です。セルごとに「進入を許す側」「退出を許す側」「ある側から入った場合に退出できる側」を区別して持ちます。

`enterFrom` は進入できる側、`exitTo` は退出できる側です。`transitions` は進入側をキーにして、許可する退出側の配列を持ちます。例えば `transitions.west: ["east", "north"]` は、西から入った場合に東または北へ出られるという意味です。キャラクターの向きや旋回で進入側を変更してはいけません。

次は西からのみ入り、東にのみ抜けられる2Dセルの設計例です。

```json
{
  "enterFrom": ["west"],
  "exitTo": ["east"],
  "transitions": {"west": ["east"]},
  "directPlacement": "deny"
}
```

セルは占有可能な空セルとして別に定義します。この例は壁セルへの侵入を許可するものではありません。3Dでは同じ記法に `up` と `down` を加えられます。例えば `transitions.down: ["east"]` は下側から登ってきた場合に東へ出る接続ですが、登るための経路や足場の検査も必要です。

省略時は従来互換とします。`enterFrom` / `exitTo` の省略は全方向を候補にし、空配列は全方向を拒否します。`transitions` 全体の省略は入口と出口の組合せを制限しません。`transitions` がある場合は列挙した組合せだけを許可し、記載されていない入口や空配列の出口は拒否します。最終的な許可は、この三条件と地形・境界・水・足場・能力条件のすべてを満たした場合に限ります。

入口と出口が同じ側の組合せは、そのセルへ入った後で同じ隣接セルへ戻るUターンです。北から入って北へ戻る例なら `transitions.north` に `north` が必要です。待機やその場での旋回は、セル間通行の組合せには含めません。

入口依存の制限を採用する場合は、現在セルへ入った側を状態とセーブへ保存する必要があります。転送・初期配置には入口側がありません。`directPlacement` は `deny`（直接配置禁止）または `allow`（入口依存の制限を適用せず配置し、退出側の制限は適用）とし、`transitions` のあるセルでは指定必須とします。既存マップは入口依存制限を持たないので移行時に入口側を捏造しません。経路移動でも最後の区間から到着セルの進入側を記録します。

### 5.2 境界の方向別通過

境界は基準セルA=`at` と、`side` の方向に隣接するBを結びます。「片面だけ通す」は、AからBとBからAを別々に指定することです。東向きか西向きかという画面上の方角ではなく、宣言のAとBに対する向きで保存します。

次はAからBだけ人物が通り、水は両方向とも通らない境界状態の設計例です。例のAの `side` が `east` なら、西側のAから東側のBへだけ通れます。

```json
{
  "passage": {"aToB": true, "bToA": false},
  "water": {"aToB": false, "bToA": false},
  "support": false
}
```

現在の真偽値を方向別形式へ移す場合、`true` は両方向true、`false` は両方向falseに相当します。2Dにも共有辺の一覧を導入し、同じ規則で扱います。閉じた壁は両方向false、一方通行扉は片方向だけtrueです。支持は足場の性質なので、人物の通行方向へ変換しません。

水を一方向だけ通す設定は逆止弁などの拡張に使えますが、現行の通水は双方向です。方向別形式を追加するだけで済ませず、水の再配分・排水判定も対応させます。人物の一方通行設定から水の流れる方向を推測しません。

### 5.3 接続全体の判定

Aから隣接Bへ移動するときは、Aの退出側の許可、Aの進入側に対応する内部接続、共有境界のAからBへの許可、Bの進入側の許可、Bの占有条件をすべて確認します。3Dでは上下経路の存在、経路中の各セルと各面も確認します。いずれかが拒否すれば移動は成立しません。

逆方向の可否は別に判定します。AからBが許可でもBからAが許可とは限りません。セル内接続と境界の制限を分けることで、「北から入ると東へ抜ける床」と「西から東にしか通せない扉」を混同せず定義できます。

入口依存の制限を入れた後の到達性検査は、位置だけでなく進入側も含めて探索します。経路リンク、退避、転送、読込時の現在地検査、Viewの操作可否も同じ判定器を使う必要があります。行き止まりを意図する場合は、帰還や解放操作を併せて定義します。

## 6. 水・足場・描画との関係

水没度0は乾燥、1〜3が足元、4〜6が腰、7〜10が完全水没です。表示用のwaterDepthは0〜3へ変換します。水没度6以上の進入・経路通過には潜水の備えが必要です。3Dの水没度は水平連結区域全体に作用し、下穴がある区域では下部へ操作を渡します。上の別セルに乾いた橋と足場があれば、下の水没セルを通った扱いにはなりません。

貯水は隣の四セルだけで判定せず、通水可能な六面からつながる区域、底、越流できる高さ、区域外への開口で判定します。複数の同じ高さの空セルで一つの貯水区域を構成できます。上を密閉する必要はありません。水は壁セルや通水不可の境界を通れず、人物だけが通行不可の格子は通れる場合があります。

現行2D地下水道は `compartment_water` の区画全体を給水・排水し、水密扉を介して接続します。退避した `waterworks` は0〜10の潮汐水没度、0〜3の表示水深、潜水・濡れの規則を保持します。通常ロードへ混ぜず、旧3Dの区域計算とも区別します。`air_supply` を持つ沈没城は、水中で空気を消費しながら移動する既存の固有ルールを持ちます。一般の3D潜水技能が実装済みという意味ではありません。

Viewへ渡す `blocked` は通行不可、`opaque` は視線を遮る描画、`wall` は壁の表示、`floor` は床表示、`waterDepth` は水深です。通常2Dはセルレイヤーから、退避3Dは空・密と足場から表示を投影します。すべてを一つの「壁」へまとめません。現行3Dの横四面は `edges` / `boundaries` に投影し、閉じた面を描画します。六面の通行可否と現在のzの断面表示は別の情報です。

素材画像はダンジョンの `art.floor` / `art.wall` などから取得します。床材を貼っても足場は生まれず、通行不可の水を壁画像へ変換しません。詳細は[表示契約](ui/VIEW_CONTRACT.md)と[描画修正記録](ui/DUNGEON_RENDER_REVIEW.md)を参照してください。

## 7. 2Dを保持するための互換性

`voxels` のないマップは2D方式のまま読み、現在地のz省略は0として扱います。立体地形の参照関数から見る場合だけ、2Dの上下z=-1とz=1を密として扱います。2Dへ移動可能な追加階層を生成する意味ではありません。

踏査キーは2Dが `x,y`、3Dが `x,y,z` です。`tiles`、既存階段・ワープ、地形パッチ、水位周期、旧セーブの座標・スクリプト継続位置を保持します。2D用の原稿・Schema・実行経路も保守対象です。

3Dマップは一つの `voxel_space` 部品が地形・六面・掘削・経路・水を管理します。2Dの地形パッチ部品を同じ立体マップへ自動適用しません。方向別制限を追加するときも、定義のない既存2Dマップの通常移動を変えません。

## 8. 実装・編集・検証の参照先

[マップSchema](../data/schemas/map.schema.json)と[立体Schema生成定義](../tools/voxel-schema.mjs)が現行JSONの形式です。[エンジン](../src/core/engine.js)の `walkable` / `move` が占有と通常移動、[立体地形](../src/core/voxels.js)が隣接・共有面・足場・水、[立体部品](../src/core/systems/voxel-space.js)が経路・操作・退避を担当します。[立体検証](../src/core/voxel-validation.js)が共有面の重複、六方向の連続性、経路、保存状態を検査します。

2Dの基礎配置は[コンテンツ生成器](../tools/build-content.mjs)と[ダンジョン生成器](../tools/build-dungeons.mjs)を確認します。追加配置・変更の編集元は[ダンジョン原稿](../authoring/dungeon-content.json)、[地形原稿](../authoring/terrain-content.json)、[立体原稿](../authoring/voxel-content.json)などです。対象マップの生成元を確認して編集し、配布先 `data/maps` のみを書き換えても再生成で失われる点に注意してください。

現在の検証例は[立体テスト](../tests/voxels.test.mjs)、[ダンジョンテスト](../tests/dungeons.test.mjs)、[環境テスト](../tests/environment-dungeons.test.mjs)、[水面・床・遮蔽テスト](../tests/dungeon-surfaces.test.mjs)にあります。方向別制限の導入時は四方16組・六方36組、Uターン、片方向境界の逆走、入場履歴の保存、2Dの省略時互換、経路・退避の可否を追加検証します。

セルレイヤーは1.16.0で実装済みです。第5節の入口依存・方向別制限は設計段階で、ゲーム処理には追加していません。
