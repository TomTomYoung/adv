# クエスト別の想定攻略パーティーと実操作テスト

[クエスト攻略パーティー試遊](../../quest-party-playtest.html)で、初版210件・第2版300件を選択し、探索・会話・戦闘から結末まで操作する。通常のGameEngine、SceneView、戦闘演出・SEを使用する。本編セーブは読み書きしない。

## 想定の内容

[定義の正本](../../playtests/quest-parties.json)に、シナリオ版とクエストIDごとの開始レベル帯、標準レベル、3編成、有限の支給品、確認する結末を記載する。同じIDでも版を区別する。

初期値は各依頼の推奨レベルを標準とし、原則として前後1レベルの範囲とする。Lv.1未満は切り上げる。メンバー全員を選んだ開始レベルにそろえ、職業の実際の成長率から能力値と技能を計算する。能力値の直接強化、無限回復、検証用の強力な技能は使用しない。試遊中の経験値獲得とレベル上昇は本編どおりに進み、開始時と終了時のレベルを記録する。

編成は基本4人、守備・回復、探索・道具、支援・槍を基に、依頼ごとに3案を指定する。仲間の連作では受注に必要な本人を各案に加える。全28種類の編成定義があり、最大5人。装備は各職業に適合する基本武器と防具。技能熟練度は初期状態から開始し、人物レベルによる習得条件は適用する。

これらは比較・調整を始めるための攻略想定であり、全依頼の全編成がクリア可能だと認定したデータではない。実操作の記録を積み重ね、難しすぎる依頼のレベル帯・装備・支給品・編成または本編の難度を調整する。

## 操作手順

1. シナリオ版、クエスト、パーティーを選ぶ。ID・依頼名・地域で絞り込める。
2. 想定範囲内の開始レベルと、到達を確認する結末を選ぶ。
3. 開始地点、戦闘方式、乱数シードを指定し、開始する。
4. 下のゲーム画面で、選択肢・移動・探索・戦闘を操作する。矢印キーで移動、Enterで決定する。
5. 到達結果と残HP・MPを確認する。同じ条件でやり直す、または別編成・別レベルを選んで再試行する。
6. 比較履歴から過去の条件を再選択し、必要に応じて結果JSONを保存する。条件URLのコピーでも開始条件を共有できる。

設定欄を変えただけでは進行中の試遊は変化しない。開始ボタンで新規の試遊に切り替える。やり直すボタンは進行中の試遊を開始したときの条件を使う。

## 開始地点と前提履歴

受付からは、受注済みの状態で依頼の受付地点に立つ。以後の現場への移動、道中の遭遇、消耗と補給を含めて確認する。通常の探索手帳で現在の行き先を確認できる。

最初の現場からは、受注後の最初のイベント地点まで移動を省略して開始する。そこから先の移動や戦闘は通常どおり行う。q006の水没した開始地点だけは、開始前に実際の排水盤操作を実行し、その準備を結果のsetup.actionsに記録する。受付からの確認では排水を代行しない。両開始方式の結果は区別して比較する。

前提クエストは必要な履歴だけを開始用に設定する。AND条件は全条件、OR条件は先頭の成立候補を使用する。前提の完了履歴による報酬・経験値・勝利数は加算しない。前提の物語は旧経路の完了履歴として保持し、対象依頼の物語・所持品・戦闘状態には適用しない。入域済みの開始地点には必要な訪問・通行登録も設定する。

この方式は依頼単位の切り出し検証である。そこまでのキャンペーン全体、加入・装備の入手経路、前提依頼の特定の結末や取得物を引き継いだ全組合せは別途確認する。対象依頼自身を完了済みにする処理はない。

## 判定と記録

指定結末でクリアは、対象依頼のstageがcompletedになり、選択した結末に到達し、途中の全滅・救助がなく、メンバーと職業が開始時と一致する場合に記録する。

別の結末で完了、全滅・救助、編成変更後の完了は別の結果として扱う。戦闘に勝っただけでは依頼クリアにならない。探索中の救助も全滅判定に含める。終了した試行はそこで固定し、再試行は新しい初期状態から始める。通常の道具使用・購入・装備変更・陣形変更は可能なので、初期・最終装備と物資の残数を併せて評価する。

結果JSONには次を保存する。

- シナリオ版、クエスト、編成、開始レベル、シード、開始地点、戦闘方式、指定結末、定義改訂番号。
- 結果、到達結末、行動数、移動歩数、戦闘数・勝利・逃走・敗北・救助数。
- 開始時と終了時の人物・職業・レベル・HP・MP・装備、所持金、増減した物資の開始・終了個数。
- 開始用に設定した前提履歴、現場開始による省略、追加の開始準備。

物資欄は純増減であり、途中の購入と使用を相殺しない消費総数ではない。結果は試したシードと経路についての観測であり、全乱数・全経路でのクリア保証ではない。

直近100件の終了記録は専用のブラウザー保存領域adv.questPartyTrials.v1に保持する。本編の記録には書き込まない。ブラウザーの保存制限時も表示中の記録はJSONとして保存できる。未完了の現在試行もJSONのcurrentに出力する。

## 定義形式

JSONのschemaVersionは形式の版、revisionは攻略想定を変更したときに上げる改訂番号。questsの下をe1/e2、さらに固定のクエストIDで区切る。表示順や表示番号には依存しない。

以下は正本の部分例。

```json
{
  "level": { "min": 1, "standard": 1, "max": 2 },
  "parties": ["balanced", "sustain", "explore"],
  "supplies": "short",
  "expectedOutcomes": ["informed"],
  "note": "推奨Lvを中心とする初期想定。結末・道中の消耗・全滅の有無を実操作で検証。"
}
```

partiesは同じファイルの編成IDを参照する。各編成のmembersは実在する人物IDの配列、nameは表示名、tacticは役割の説明。人物ごとのloadoutsはjobとequipmentの配列を持つ。複数の装備が同じ部位を占める設定は拒否する。suppliesはgoldとitemsの有限個数を持つ。expectedOutcomesは実在する結末IDで、画面の初期選択に使う。画面では別の実在結末を指定して比較することもできる。

同一依頼にメンバー構成の異なる2案以上を必須とする。現在の正本ではすべて3案。人数上限、人物・職業・装備・道具・結末の参照、レベル範囲、同伴条件、依頼の定義漏れも検査する。

## 検証

node --test tests/quest-playtest.test.mjsで両版の全3,060開始ケースとセーブ状態の整合性、境界レベル、不正定義、開始前の排水、再試行の再現性、元データの非変更、Lv.1の2編成によるq001実経路を検査する。

[ブラウザーテスト](../../tools/browser-quest-party-smoke.mjs)では実HTMLの選択と操作、結果・再試行・JSON出力、版ごとの同伴条件、モバイル表示を確認する。全510件のクリアを自動認定するテストではない。

実装は[試遊モデル](../../src/application/quest-playtest.js)と[画面](../../src/quest-party-playtest.js)。通常のゲームバランスや本編データはこの定義の変更によって変わらない。
